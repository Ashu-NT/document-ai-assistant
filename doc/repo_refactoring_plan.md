# Repository Refactoring Plan — Large File Decomposition & Duplicate-Code Consolidation

## Status: DRAFT — for team review before implementation. No code has been changed.

## 1. Purpose and Ground Rules

Several files in this repository have grown past the point where they hold one clear responsibility, and several small helper functions have been reimplemented independently in multiple files instead of being written once and shared. This document is a full-codebase scan and a concrete proposal for fixing both problems, split into phases the team can review and execute independently.

**Ground rules for every phase below (non-negotiable):**

1. **No functional behavior changes.** This is a pure structural refactor — same inputs produce the same outputs, same log lines, same exception types. Behavior-preserving performance improvements (see section 6) are the one exception, and are called out as a separate, optional, later phase — never bundled into a structural split.
2. **One file, one responsibility.** Mirrors the convention already documented in `doc/repo_design.md` and already visible in the codebase itself (e.g. `application/reporting/retrieval_benchmark/{writers,renderers,serializers,summaries,diagnostics}/`, `infrastructure/db/mappers/extraction/` one-file-per-entity, `application/langgraph/retrieval_strategy/{constants,executors,models,planners,policies,selectors,services,tracing,validation}/`).
3. **Group by domain first, role second — avoid flat folders.** New subfolders nest *inside* the existing domain folder they belong to (e.g. `retrieval/intent/`, not a new top-level `intent/`). Every new subfolder proposed below is justified against sibling folders that already exist in that same area — nothing here invents a top-level folder or duplicates an existing sibling's purpose.
4. **Shared code lives in the nearest real "common" layer, not copy-pasted.** When the same logic appears in 2+ files, it moves to one shared module that all consumers import. Where the existing codebase already has a `shared/`-style folder for that domain (e.g. `src/application/workflows/shared/`), new shared helpers land there; where no such folder exists yet at the right scope, this plan proposes exactly one new one (e.g. `src/shared/progress/`, `src/application/langgraph/common/`).
5. **Verify after every phase**, exactly the same way this codebase already does after every other change: parse-check touched files, run the directly-affected test file(s), then run the full `tests/unit` suite, then a `ruff check --select F401,F841,F811` pass over touched directories. No phase is "done" until that sequence is green.
6. **No new abstractions beyond what's needed.** Several files were deliberately *not* split below because a large file is not automatically a multi-responsibility file — see the "Do not split" call-outs throughout. Forcing a split where none is warranted is exactly the kind of churn this plan is trying to avoid causing.

## 2. Scope and Methodology

**Scope:** every `.py` file under `src/` exceeding 250 lines (tests were not included in this pass — flagging as a possible follow-up scan, not covered here).

**Method:** a full-repository line-count scan found **72 files over 250 lines**. Given the volume, seven parallel research passes were run, one per domain cluster, each reading every assigned file in full (not excerpts) plus the surrounding directory structure, and each independently proposing: (a) the distinct responsibilities bundled in each file, (b) a concrete split into new files/folders, (c) duplicate logic found across files that should be shared instead of copy-pasted, and (d) inefficiencies worth flagging (not fixing). This document reconciles all seven reports into one plan, resolving the handful of places where two clusters independently found the *same* duplication (noted explicitly where that happened) into one canonical shared module rather than two competing proposals.

**Totals:** 72 large files → **~230 new single-responsibility files** + **~20 new shared/common modules** consolidating **34 confirmed cross-file duplications** (several appearing 3-4 times independently across unrelated files).

**Threshold update (post-review):** the team has since raised the "needs splitting" bar from >250 to **>300 LOC**. This does not change section 3 (shared-code consolidation) at all — duplication removal is about correctness/maintainability, not file size, so every item there still applies regardless of the file's resulting length. It **does** exempt 22 files that were between 251-300 LOC from mandatory splitting; each is marked `[EXEMPT — ≤300 LOC threshold]` in section 4 below, with its file-split proposal kept only as an optional future reference. Any shared-code extraction from section 3 that happens to touch one of these files still happens — that part of the plan is unaffected either way.

## 5. Phased Execution Plan

Each phase is independently reviewable, testable, and revertible. Run the full verification sequence from section 1, rule 5, after every phase before starting the next.

- **Phase 0 — Baseline.** Full `tests/unit` run + `ruff check` on the whole `src/` tree, recorded as the "before" baseline every later phase's green run gets compared against.
- **Phase 1 — Shared/common code extraction (section 3).** Create every new shared module, migrate one consumer at a time within each module (so a mid-phase revert is always possible), delete the duplicate from each old location as its consumer is migrated. This phase touches many files with tiny, low-risk diffs (import + delete duplicate) — no file is restructured yet. Item #33 (field-alias triples) and #34 (evidence-merger skeleton) are explicitly excluded from this phase pending a team decision.
- **Phase 2 — Extraction/Ingestion workflows (4.2).** The two largest files in the repo; doing them early means every later phase benefits from the `common/` modules Phase 1 already created (settings_resolver, confidence_coercion, concurrent_chunk_runner, enum_label_resolver) landing in their final shape before other clusters lean on them too.
- **Phase 3 — Parsing/Chunking (4.1).** Largest file count (17); independent of phases 2/4-7.
- **Phase 4 — Retrieval + Question-Answering workflows (4.3).** Independent of phases 2/3/5-7.
- **Phase 5 — LangGraph, part 1: graphs/evaluation/planning (4.4).** Depends on Phase 1's `answer_intent_resolver`/`plan_tool_spec`/`value_coercion`/`agent_eval_metric_registry` shared modules already existing.
- **Phase 6 — LangGraph, part 2: reflection/routing/research/retrieval-strategy (4.5).** Depends on Phase 1's `retrieval_strategy_state_adapter`/`answer_intent_resolver`/`identifier_value_pattern` extension already existing; can run in parallel with Phase 5 if the team has bandwidth for two reviewers, since the two LangGraph sub-clusters touch disjoint files.
- **Phase 7 — Answer-generation services + agent_runtime (4.6).** Get explicit team sign-off on the one moderate-confidence item (`answer_generation_service.py`) before touching it; everything else in this phase is high-confidence.
- **Phase 8 — Evaluation/Reporting/Tools/Infrastructure (4.7).** Includes the ORM mixin (#31) — coordinate with anyone who has in-flight Alembic migrations, since this phase touches ORM class definitions (column *values* and table names are unchanged, only how the columns are declared in Python, but review this carefully with whoever owns migrations before merging).
- **Phase 9 (optional, separate from structure) — Efficiency improvements.** See section 6. Do not bundle into any phase above.

Phases 3-8 have no file overlap with each other and can be reordered or parallelized across reviewers freely once Phase 1 and Phase 2 land; the ordering above is a suggestion (biggest/highest-risk files first), not a hard dependency chain beyond "shared modules exist before their consumers are split."

## 6. Efficiency Flags (not part of the structural refactor — separate, optional follow-up)

These were noticed while reading files for the structural analysis above. None are proposed as fixes in this plan — each would need its own isolated, tested change, reviewed on its own merits against the ground rule that behavior must not change. Listed here so the team can decide which (if any) are worth a dedicated follow-up phase.

- **`chunk_semantic_signal_extractor.py`** — marker-hit scanning is O(fragments × chunk_types × markers) via repeated substring scans; a precompiled regex alternation would help.
- **`toc_page_range_strategy.py`** — TOC-entry-to-header matching runs up to 3 full passes over candidate headers per TOC entry.
- **`document_graph_builder.py`** — asset-metadata sync does a second full O(elements) pass after the main materialization loop already visited every element once.
- **`section_hierarchy_resolver.py`** — contextual-parent lookup is worst-case O(headers²) for documents with many unnumbered headers.
- **`canonical_ocr_merger.py`** — duplicate-text detection and insertion-index resolution each rebuild a full per-page element scan per OCR execution result, repeated per fallback target on the same document.
- **`structured_section_fragment_builder.py`** — window collection re-scans all ordered elements once per spec (O(specs × elements) per section; up to 13 specs for datasheet documents).
- **`extraction_workflow.py`** — `_resolve_maintenance_task_id`/`_resolve_equipment_id` do two full linear scans per lookup, called once per extracted item; `_pick` rebuilds a normalized copy of the entire payload dict on every field access (5+ times per entity).
- **`extraction_response_sanitizer.py`** — the same `_pick`-rebuilds-whole-dict issue, doubling the cost across two call sites (see shared-code #9 — fixing the duplication also removes this double cost).
- **`extraction_result_merger.py`** — re-normalizes the same strings on every dict-key computation inside per-entity merge loops instead of once per item.
- **`post_classification_chunk_finalization_workflow.py`** — chunk-structure-match comparison builds full signature tuples including complete `chunk.content`/`embedding_text` strings just to test equality, holding two full-text copies in memory; a hash/digest comparison would avoid this.
- **`agent_eval_runner.py`** — tool-policy membership checks (`tool_name not in tool_names`) use a `list`, not a `set`.
- **`intent_router.py`** — planned-task/deep-research detectors each rebuild padded strings and re-scan overlapping marker tuples independently on the same input within one `route()` call.
- **`retrieval_signal_extractor.py`** — `_matches_term` builds and compiles a fresh regex string per term per call — potentially a few hundred ad-hoc regex compilations per single `extract()` call, none cached at class/module scope.
- **`deterministic_research_planner.py`** — `_extract_identifier_value`'s regex is compiled inline inside the function body (not module-level), recompiled on every call, up to twice per concept.
- **`research_gap_detector.py`** — two focus-term-coverage helpers independently rebuild the identical per-evidence-item normalized haystack string instead of computing it once and reusing it; both are O(items × focus_terms).
- **`answer_intent_analyzer.py`** — chunk-content signal scoring makes 7+ separate full passes over the retrieved-chunk list for related checks that could be collected in one pass.
- **`event_stream_adapter.py`** — two answer-question narration helpers each independently re-run the same keyword-category check against the same normalized question string per node event.
- **`sql_keyword_scorer.py`** (3 related flags) — per-query-invariant text compaction is recomputed on every one of N candidate-row scoring calls; per-identifier containment checks retokenize the same content text once per identifier instead of once total; content/section text is tokenized twice per row via two independent regex passes.
- **`retrieval_query_intent_inferer.py`** — the typo-tolerant fuzzy fallback tier is O(tokens × markers) per call via `difflib.get_close_matches`, only reached when the primary scoring tier finds zero hits.
- **`structured_evidence_resolver.py`** — entity resolution issues one resolver call per entity type in a loop (up to ~9 types) — a potential N+1-shaped pattern across types per query.
