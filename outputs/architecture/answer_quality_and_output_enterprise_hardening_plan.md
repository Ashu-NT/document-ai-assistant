# Answer Quality & Output Enterprise Hardening — Investigation and Plan

## Status

- **Investigation only. No code has been changed.** This document reports findings from a deep, six-angle read-only audit of the path from "chunks retrieved" through LLM answer generation, reflection, guardrails, and CLI rendering, and proposes a phased plan for the team to review before any implementation starts.
- Trigger: the team reported that final answers often don't feel good-quality even when retrieval surfaced good chunks, and separately raised concern about the reliability of the "reflection" self-check layer.
- Method: six parallel, independent code audits (prompt/context assembly, the LLM call and `AnswerGenerationService` internals, the reflection subsystem, guardrail impact on user-visible output, CLI rendering, and answer-quality measurement), each reading the real current code — not prior architecture docs — and reporting findings with file:line evidence. This document reconciles and organizes all six into one picture.

## 1. Executive Summary — why "good chunks retrieved" does not mean "good answer seen"

The team's framing ("good chunks might be retrieved, but output isn't good") turns out to be structurally accurate, and not attributable to one bug. There are **five independent leak points** between retrieval and what the user actually reads, any one of which can silently degrade a turn that started with good evidence — plus a sixth, cross-cutting problem: **there is no automated way to know how often this happens or whether a fix helps**.

1. **Evidence gets crushed on the way into the prompt.** The raw, human-readable source text shown to the model is capped as low as 2 sources × 350 characters, ranked with no regard for retrieval relevance score (which is computed and then never read again), while the structured JSON evidence payload sent alongside it has no size cap at all — the budget is inverted relative to risk. (Section 2)
2. **The model has no repair path when its own output is malformed.** One JSON hiccup — plausible given a locally-hosted reasoning model whose `<think>` blocks must be regex-stripped before parsing — fails the entire turn with a generic error and no retry, unlike the extraction pipeline elsewhere in this codebase which does retry. (Section 3)
3. **A wrong intent guess can silently swap a real LLM answer for a narrow deterministic snippet.** Answer-intent classification runs on generic bare-keyword heuristics ("model," "service," "tag") and, if it misfires toward `IDENTIFIER_LOOKUP`, bypasses the LLM entirely in favor of a renderer that can't detect a compound question and will silently answer only half of it. (Section 3)
4. **Reflection — the layer meant to catch exactly this — is off by default, and even when on, its two quality scorers are cheap, gameable proxies, not real relevance/faithfulness checks.** A fluent-but-wrong answer with one citation and a couple of question-word repeats scores a perfect quality score today. (Section 4)
5. **The guardrails built to catch citation/claim problems are functionally inert.** Two of five actually inspect the answer; both are warn-only and their findings are traced, precisely, into a diagnostics dict four levels deep that no renderer — console, JSON, or Markdown — ever reads. The one guardrail mechanism that does change what the user sees is an older, separate, cruder text-regex layer that can, in one specific interaction, be silently undone by unrelated recovery logic. (Section 5)
6. **Even when everything upstream worked, the CLI hides the evidence of it.** Citations never show a page number the user could check. The link between a section and the reference notes that support it is computed and then discarded. Reflection's stated reason and any limitation note are demoted to bare footer trivia, with no more visual weight than an elapsed-time counter. One of the two shipped CLIs cannot show any of this regardless of flags. (Section 6)
7. **There is no automated measurement of generated-answer quality anywhere in this codebase** — the retrieval benchmark measures retrieval, agent-eval measures routing/planning/safety, and reflection's own scores are never logged or aggregated. Every fix proposed below is currently unverifiable except by manual spot-check, and a future regression would go undetected indefinitely. (Section 7)

None of these is described here as "the" root cause — they compound. A turn can lose quality at context-assembly, again at generation, again at the (disabled or weak) reflection gate, again at the (inert) guardrail layer, and again at rendering — each stage assuming an earlier stage already handled it.

## 8. Phased Enterprise-Hardening Plan (for team review — nothing below is implemented)

Ordering rationale: instrumentation first (so every later phase is measurable), then the highest-leverage silent-failure fixes (generation and context-assembly), then reflection and guardrails (the safety net), then presentation (making real signal visible), with the stub-guardrail buildout kept as an explicit, separately-scoped follow-on since it was already raised and paused earlier in this engagement.

### Phase 0 — Instrumentation & baseline (do this first)
Close the Section 7 gap before changing behavior elsewhere, so every subsequent phase has a before/after signal instead of relying on anecdote.
- Small hand-authored golden set (question + expected answer/claims + expected citations), scored by an independent LLM-as-judge pass, run as its own report — reusing existing truth-set/case plumbing rather than the substring-only agent-eval fixture.
- Log reflection's per-turn scores (`answer_quality_score`, `evidence_quality_score`, `overall_score`, decision) using the same structured-logging pattern `retrieval_query_intent_inferer.py` already establishes, plus a small aggregation script mirroring `report_retrieval_intent_fallback_rate.py`.
- Capture the actual prompt text sent to the model in diagnostics (or at minimum on request, gated to avoid bloating every response) — closes 3.5.
- Surface the canonicalizer's existing-but-discarded counters (2.8) as real diagnostics.

### Phase 1 — Stop silent generation failures
- Add a bounded retry-with-repair loop for malformed/schema-invalid LLM JSON, mirroring the extraction pipeline's existing `ExtractionBatchRetryCoordinator` pattern (3.1).
- Set an explicit, tuned temperature (and consider per-intent tuning) for answer generation instead of provider defaults (3.2); set an explicit context-window/output-length bound (3.6).
- Give the deterministic identifier/spare-parts renderers a way to detect a compound question and fall through to the LLM for the part they can't answer, or at minimum emit a `limitation_note` when they only address part of the question (3.3).
- Replace the two narrow `except Exception` model-fallback paths with an explicit, logged fallback so a settings failure can't silently swap in a materially weaker model (3.7).

### Phase 2 — Fix evidence fidelity into the prompt
- Rebalance the raw-source vs. structured-JSON budget: make raw-source inclusion actually use retrieval relevance score (currently computed and discarded), and cap the JSON payload's size (2.1, 2.2).
- Only expose `source_number`s in the JSON payload that are also present in the raw appendix (or teach the citation guardrail to check "was shown as text," not just "resolves to a chunk_id") (2.3).
- Fix the source-level (not row-level) table-row canonicalization drop (2.5).
- Add an explicit grounding-rule instruction for contradictory evidence across sources (2.4).
- Decide whether format-policy instructions need enforcement/verification or should stay soft (2.6); consider re-anchoring the question near the point of generation (2.7).

### Phase 3 — Make reflection an actual safety net
- Decide, as a team, whether reflection should default on (with a real cost/latency tradeoff conversation) or whether its absence should at minimum be visibly surfaced to the user/operator (4.1) — this is the single highest-leverage decision in this whole plan.
- Replace `EvidenceQualityScorer`'s presence/metadata proxies and `AnswerQualityScorer`'s lexical-overlap proxies with a real relevance/faithfulness signal — the newly available `reference_notes[*].chunk_id` (unresolved = hallucinated citation) is a precise, already-computed signal reflection currently ignores entirely (4.2, 4.3, 4.6).
- Constrain the validator so keyword/regex downgrades can only tighten a stricter LLM/deterministic verdict, never loosen a correct FAIL/CLARIFY into a false ACCEPT; require `clarification_question` to be a non-empty invariant rather than patched around downstream (4.4).
- Require deterministic RETRIEVE_AGAIN branches to always produce a real reformulated query, not boilerplate append text (4.5).

### Phase 4 — Make guardrails matter
- Thread `post_answer_guardrail_warnings` all the way to `GraphResult.data` and at least one renderer — closing the traced 4-level dead end (5.1).
- As a team decision: keep `CitationGuardrail`/`UnsupportedClaimGuardrail` warn-only but actually visible, or graduate them toward blocking/regeneration now that they'd be visible (5.2).
- Decide the fate of the 3 no-op stub guardrails — this connects to and can resume the guardrail-implementation investigation already started earlier in this engagement (5.3).
- Reconcile the older `PostResponseGuardrailService` (the only mechanism that currently mutates answer text) with the newer structured guardrails instead of leaving two disconnected systems (5.4); fix the safe-failure-recovery string-match collision that can undo a guardrail's fallback (5.5).

### Phase 5 — CLI/presentation overhaul
- Render real, checkable citations (page/section), not just a count (6.1).
- Render reference notes grouped under the section they support, using the already-computed `reference_note_ids` link (6.2); resolve the `answer_text`/`sections` duplication (6.3).
- Make the `(unverified)` marker visually prominent, not a trailing suffix (6.4).
- Always show reflection's reason and give `limitation_note` real visual priority, not footer parity with elapsed time (6.5, 6.6).
