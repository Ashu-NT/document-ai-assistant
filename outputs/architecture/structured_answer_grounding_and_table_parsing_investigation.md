# Structured-Answer Grounding & Table-Parsing — Investigation and Upgrade Plan

## Status

- **Investigation only. No code has been changed.** This document independently verifies an external review's findings (pasted CLI transcripts against the current system) with five parallel, read-only code audits, each grounded against real ingested-document data in `data/maintenance_ai.db` (read-only SQL only — no LLM available in this environment, no writes). Every finding below was reproduced or directly confirmed against real stored rows, not assumed from the transcripts alone.
- Trigger: after the team implemented the per-category presentation upgrade (table-grid rendering, an extended `KeyValueExtractor`, and new `TableSchemaInferer`/`TableProjector` components), an external review of real CLI output found the output "looks better than before but not enterprise standard" — specifically: mixed/partial context despite tables being "well hydrated," unreliable structured row extraction, critically broken evidence scoping, overly verbose output exposing internal fallback data, and weak reflection.
- **Constraint honored throughout this document**: real document data (`data/maintenance_ai.db`, ~18 ingested documents) was used only to *ground and reproduce* each finding — every root cause and proposed fix below is described in general, schema-driven terms applicable to any document this system ingests, not hardcoded to the specific document used for verification.
- Method: five parallel code audits — table schema inference/row-parsing, evidence-scoping architecture, maintenance interval column-mapping, reflection scoring + strategy advisor, and output verbosity/raw-data exposure — synthesized here into one picture.

## 1. Executive Summary

**The external review's core diagnosis is correct, and this investigation independently confirms every major claim with exact file:line evidence and, in most cases, direct reproduction against real data.**

| Area | External review's claim | This investigation's independent verdict |
|---|---|---|
| Evidence scoping | "Critically broken" — retrieves correct pages but answer isn't strictly generated from them | **Confirmed, with exact mechanism.** Troubleshooting (and, architecturally, procedure-steps) resolve structured records by `document_id` only — no chunk/page/table scoping. Reproduced against real DB data: the exact document has 3 troubleshooting rows at pages 10/10/11, while genuinely-retrieved pages 89/96 have real troubleshooting content with zero extracted entities — reproducing the transcript's exact mismatch. |
| Structured row extraction | "Unreliable" | **Confirmed, two independent bugs**, both reproduced against real stored table data: a merged legend header (`"M  S  A"`) causes the same cell to become both the task and the interval; a two-column table's single-item cells get silently demoted to unstructured "raw row" fragments (14 of 48 real items lost in the reproduction). |
| Output formatting | "Too verbose, exposes internal fallback data" | **Confirmed.** Raw-row fallback text is unconditionally included with no gate of any kind — not even an unused/dead flag exists today. Can roughly double an answer's length. |
| Reflection | "Accepts answers that should be rejected" | **Confirmed, with the exact arithmetic.** The reported repeated `0.8334` score is not a coincidence — the scoring formula is a coarse boolean average with effectively ~7 achievable values, so two structurally different bad answers land on the same bucket. No check exists anywhere for "are the pages cited in the answer a subset of the pages actually retrieved" — confirmed absent by direct search — which is exactly the check that would have caught the troubleshooting mismatch. |
| Strategy advisor | Not fully explained by reviewer, flagged as "adding latency without improving results" | **Confirmed as a real bug, not conservative-by-design.** Its validator does a literal verbatim-substring check of extracted concepts against the raw query text — rejects nearly all realistic paraphrased/category-label concepts. The one existing unit test only passes because its query happens to contain every concept word verbatim. |

**The single most important finding, confirmed independently**: the "grounding-boundary failure" is real and has an exact root cause — `StructuredEntityResolver`/the DB reader layer for troubleshooting (and procedure-steps) never receives the current turn's retrieval scope (approved chunk IDs, table IDs, or page numbers) — only `document_id` and the raw question text (used in a near-always-failing literal `ILIKE` match, which is *why* it falls back to dumping the whole document's records). **Maintenance-summary rendering is architecturally immune to this specific bug** (it's built directly from retrieved chunks, not a separate document-wide DB query) — but has its own, independent unscoped-evidence problem (no per-chunk topicality filter, so off-topic pages leak in via overly broad keyword matching). Spare-parts shares the same latent DB-query architecture but doesn't currently trigger the bug in practice, due to one config difference plus a working chunk-scoped fallback path.

## 3. Findings — Table Structure Interpretation (2 independent bugs)

Scope: `src/domain/assets/table_asset.py`, `src/application/workflows/question_answering/evidence/table_evidence_hydrator.py`, `src/application/workflows/question_answering/answer_context/tables/table_header_semantics.py`, `src/application/workflows/question_answering/answer_context/maintenance/maintenance_candidate_parser.py`, `src/application/services/answer_generation/formatting/spare_parts_table_parser.py` + `position_pair_row_parser.py`/`structured_grid_row_parser.py`.

**Both bugs are answer-generation-time parsing defects, not ingestion/chunking defects** — confirmed by inspecting `elements.parser_extra_json.table_rows` directly: the ingested table grids are faithful, correct representations of the source PDF tables in both cases. Fixes belong entirely in the files listed above, not in the docling extraction or chunk-building pipeline.

| # | Finding | Evidence |
|---|---|---|
| 3.1 | **Bug A — legend/merged-header leak.** `TableAsset.to_structured_row_text()` (new code) blindly zips row-0 cells as "headers" against every other row's cells, producing `f"{header}={cell}"` strings with **no check that the table is actually key-value shaped**. `TableEvidenceHydrator` appends this output onto the same chunk content used for normal rendering. When the real header row is a merged, multi-code legend cell (e.g. `"M  S  A"` — three frequency codes glued together), `table_header_semantics.schedule_interval_label()` doesn't recognize it (it only matches exact single-code or `"every N ..."` patterns), so `AnswerTableSchemaInferer` never classifies the table as a maintenance-schedule matrix, the position/legend-aware `MaintenanceTableCandidateExtractor` never runs, and everything falls to the naive per-cell regex fallback — which grabs the same cell for both `task` and `interval`. **Reproduced exactly against real data**: every task in the real table gets emitted twice — once clean, once as `"M  S  A=<task text>"` corrupting both columns. | `table_asset.py:53`; `table_evidence_hydrator.py:76-85`; `table_header_semantics.py:88-94`; `maintenance_candidate_parser.py:133-156` |
| 3.2 | **Bug B — two-column table row loss.** `SparePartsTableParser._parse_free_text_blob`'s acceptance gate requires `len(pair_rows) >= 2` per cell (via `rows_from_position_pairs`) before accepting position/description pairs packed into one cell. A genuine side-by-side two-column layout doesn't line up evenly — many visual rows have exactly 1 item in each half-cell, not 2. Those single-item cells fail the `>= 2` gate, fall through to a 4-token free-form pattern they can't match either (2-token `"14.04  Plug (filling)"` vs. required `position qty unit description`), and get demoted to opaque `raw_rows` fragments — **losing Position/Description structure entirely even though the data was captured correctly at ingestion.** Reproduced exactly against real data: 14 of 48 real items dropped to unstructured "Raw row:" lines, with the parser's own `partial: True` flag firing even though every item is actually present in the source text. | `spare_parts_table_parser.py:127-150,155-164`; `position_pair_row_parser.py:8-20`; `free_form_position_row_parser.py:11-13` |
| 3.3 | Secondary, compounding: `structured_grid_row_parser.as_structured_header()` explicitly rejects a repeated `field_key` (`if field_key in seen_fields: return None`) — so even a *well-labeled* two-column-pair table (e.g. `"Pos | Description | Pos | Description"`) would always fall through to the same content-regex path and inherit Bug B. | `structured_grid_row_parser.py:37-58` |

## 4. Findings — Maintenance Interval Column-Mapping (grounded in the same real table as 3.1)

Scope: `src/application/workflows/question_answering/answer_context/maintenance/maintenance_candidate_parser.py`, `maintenance_task_extractor.py`, `maintenance_action_verbs.py`, `src/application/services/answer_generation/formatting/renderers/maintenance_schedule_renderer.py`.

Confirmed: **defects 1 and 3 below share exactly one root cause** (the position-blind, legend-blind fallback parser); **defect 2 is a separate bug** in the extractor's chunk-selection logic.

| # | Finding | Evidence |
|---|---|---|
| 4.1 | **Defect 1 — Interval receives Task text.** `candidate_from_table_row`'s header-less fallback branch picks `task_cell` as the first cell where `looks_like_maintenance_task()` matches (an action verb **or** an interval-keyword regex — not both required), then picks `interval_cell` as the first cell matching the interval regex. For a real row like `"Change the lubricant after every 6 months..."`, this single cell matches *both* checks (action verb "change"/"flush" **and** "every 6 months"), and since no earlier cell satisfies either, `task_cell == interval_cell` — the same string. | `maintenance_candidate_parser.py:133-156,195-204` |
| 4.2 | **Defect 2 — off-topic pages leak in.** `MaintenanceTaskExtractor`'s gate is a single global `if answer_intent != MAINTENANCE_SUMMARY: return []` — there is **no per-chunk/per-source relevance filter**. It iterates every `source` in the same unfiltered `context_chunks` working set the whole answer uses (confirmed: `sources` is a straight 1:1 map of every retrieved chunk, no chunk_type/score/topicality filter). Combined with `MAINTENANCE_ACTION_VERBS` matching on any of 17 common verbs (inspect/check/replace/clean/flush/grease/etc.) appearing *anywhere* in a line — irrespective of chunk type — a safety-warning sentence containing "flush," an unrelated technical description containing "grease" (as in "grease trap"), and a startup-checklist sentence containing "Check" all get misidentified as maintenance-task candidates. Reproduced: real chunks from `safety_warning`, `operation_instruction`, and `overview` chunk types on off-topic pages all matched. | `maintenance_task_extractor.py:52-112`; `maintenance_candidate_parser.py:189-204`; `maintenance_action_verbs.py:7-25` |
| 4.3 | **Defect 3 — real interval text stranded in Notes, same root cause as 4.1.** For a row like `["X", "", "Check gearbox for leaks", "See gearbox Annex"]`, no cell matches the interval regex (`interval = "Not specified"`), and the leftover cells (`"X"` — the actual schedule-column marker — and `"See gearbox Annex"`) get concatenated into an opaque `notes` string with **zero use of column position or the document's own printed legend** (D/W/M/Q/S/A definitions appear in the surrounding prose, just above the table). This is *not* a disconnected extraction pass — `MaintenanceScheduleRenderer` correctly uses the same `entry` object for both the table row and its Notes line — the bug is entirely upstream: the fallback parser discarded the positional/legend information needed to resolve the real interval before the candidate was ever built. Notably, the codebase already has a **correct**, position/legend-aware extractor for exactly this shape (`MaintenanceTableCandidateExtractor._matrix_candidates`, using `schedule_interval_label`/`is_positive_schedule_marker`) — it just never activates here because the merged header (finding 3.1) causes `table_kind` to degrade to `"general_table"` first. | `maintenance_candidate_parser.py:143-149`; `maintenance_schedule_renderer.py:57-67`; `maintenance_table_candidate_extractor.py:41-104` |

| # | Finding | Evidence |
|---|---|---|
| 5.1 | **The repeated `0.8334` score is a confirmed arithmetic artifact, not a coincidence of equal quality.** `answer_quality_scorer.py` averages 6 boolean signals — but `complete_enough` is *derived* from two of the other five (not independent), and `contains_page_reference`/`contains_grounding` are both driven by the same underlying "citations non-empty" boolean. ## 7. Phased Implementation Plan (for team review — nothing below is implemented)

Ordering rationale: fix the correctness bugs that produce visibly wrong data first (evidence scoping — the single most severe, "answer isn't from the retrieved pages" defect — then the two table-parsing bugs, then the maintenance column-mapping bugs that share one of those root causes); then hide what shouldn't be user-facing; then strengthen reflection so it can catch regressions in everything above automatically; then fix the advisor. Every phase's fix must be schema/architecture-general — validated against the diverse ~18-document corpus's variety of table layouts, not tuned to one document's specific content.

### Phase 1 — Evidence-scope enforcement (Priority 0: the grounding-boundary failure)

This is the fix the external review's own proposed architecture describes, adapted to this codebase's actual current structure (`StructuredEntityResolver`/`StructuredEvidenceResolver`/DB readers), confirmed by Section 2's trace:

1. **Introduce an `EvidenceScope` value object** (chunk_ids, table_ids, page_numbers, document_id) built once per turn from `RetrievalWorkflowResult.approved_chunks` (plus anything `StructuredFactJoiner` explicitly joins in) — this is the "validated evidence scope" the review calls for.
2. **Thread it into the resolution path**: `StructuredEvidenceResolver.resolve()` → `StructuredEntityResolver.resolve()` → the DB readers (`troubleshooting_entry_reader.py`, `spare_part_reader.py`, and the analogous maintenance/procedure readers). Add a scoped query method to each reader, e.g. `find_for_evidence(document_id, chunk_ids, table_ids)`, using the traceability columns (`source_chunk_id`, etc.) that already exist per finding 2.7 — this is schema-compatible with every document in the corpus, not a new column.
3. **Replace the `fallback_to_list(document_id)` behavior** for `TROUBLESHOOTING`/`PROCEDURE`/`MAINTENANCE_TASK`/`MAINTENANCE_INTERVAL`/`SAFETY_WARNING` with `fallback_to_list_within_scope(document_id, evidence_scope)` — same fallback *intent* (don't lose entities the literal-text search missed) but scoped to this turn's actual retrieved evidence instead of the whole document.
4. **Add a defense-in-depth `is_grounded()` filter at the render boundary** (`StructuredEvidenceViewBuilder`, or each renderer just before iterating `entities_of_type(...)`): `record.source_chunk_id in evidence_scope.chunk_ids or record.source_table_id in evidence_scope.table_ids` — even if a future change reintroduces a scoping gap upstream, this backstop guarantees no cross-scope leak reaches the user. This mirrors the review's own proposed check, generalized to work with this codebase's actual field names.
5. **Fix `StructuredFactJoiner`'s "manufacture evidence" behavior** (finding 2.2): once an entity fails the `is_grounded()` check, it should be dropped, not have its source chunk force-fetched and spliced in to make it look grounded after the fact.
6. Apply the same scoping to procedure-steps (finding 2.4) in the same change, since it shares the identical code path.
7. **Tests**: for each of troubleshooting/procedure/maintenance, a case where a document has structured records both inside and outside the current turn's evidence scope, asserting only in-scope records render — using synthetic fixture data, not any specific real document's content, so the test generalizes.

### Phase 2 — Maintenance's independent unscoped-relevance bug (finding 4.2)

Distinct from Phase 1 (maintenance is already chunk-scoped by construction) — this needs a per-chunk *topicality* filter, not a DB-query fix:
1. Before treating a chunk as maintenance-candidate material, require either a `chunk_type` in a maintenance-relevant set (e.g. `maintenance_interval`, not `safety_warning`/`operation_instruction`/`overview`) or a minimum keyword-density signal beyond a single incidental verb match.
2. Tighten `looks_like_maintenance_task`/`looks_like_maintenance_line` so a single generic verb match isn't sufficient in isolation — require it to co-occur with a genuine schedule/interval signal specific to that source's chunk type, or gate more strictly on chunk_type first.
3. **Test with synthetic chunks of varying chunk_types** (not any specific document) containing incidental verb matches, asserting only genuinely maintenance-typed content survives.

### Phase 3 — Table interpretation bugs (findings 3.1-3.3)

1. **Bug A (legend leak)**: guard `TableAsset.to_structured_row_text()` to only produce `"header=value"` echoes when the table is confirmed key-value shaped (reuse `AnswerTableSchemaInferer`'s existing role-matching, don't duplicate it) — skip/omit this echo for anything else, rather than blindly zipping row-0. Separately, teach `table_header_semantics.schedule_interval_label()` to recognize and split merged multi-code legend headers (tokenize on whitespace, check each token against the known code set) so genuinely schedule-matrix tables get correctly classified and routed to the existing, correct `MaintenanceTableCandidateExtractor` instead of degrading to the naive fallback. This directly fixes finding 4.1/4.3 as well, since they share this root cause.
2. **Bug B (two-column flattening)**: change `_parse_free_text_blob`'s acceptance gate to accept a single `position + description` match per cell (not require `>= 2`), while keeping a guard against genuinely free-running prose being misparsed as a position pair (e.g. require the position token to match the existing position-code pattern strictly, which already exists). Also address the compounding issue (finding 3.3): allow `as_structured_header()` to recognize a genuine repeated two-bank header (`"Pos | Description | Pos | Description"`) as two independent field groups instead of unconditionally rejecting the repeated key.
3. **Tests**: synthetic table fixtures — one with a merged multi-code legend header, one with an uneven two-column position/description layout — covering the general shape of the bug, not any one real document's exact table.

### Phase 4 — Hide fallback/internal data from normal users (findings 6.1-6.3)

1. Add `show_raw_evidence: bool = False` to `DemoVisibilityPolicy` (the natural, already-anticipated home per finding 6.3).
2. Thread it from CLI args (`--show-raw-evidence`, alongside the existing `--debug`) through `AnswerGenerationRequest` into `SparePartsListRenderer.render()`/`_render_groups()`, gating the "Raw row: ..." lines behind it — default off, so normal users never see them; the underlying data still exists for debugging.
3. Alternative/complementary approach also worth considering: move raw-row content out of the primary answer string entirely into `last_diagnostics()`-style out-of-band diagnostics (mirroring how `spare_parts_dropped_row_count`/`spare_parts_partial` already work) — only the CLI, when the flag is set, prints them separately. This keeps the core answer string clean regardless of caller.
4. **Tests**: default-off behavior (no raw rows in output) and flag-on behavior (raw rows appear), using synthetic incomplete-row fixtures.

### Phase 5 — Summarize-first for broad structured queries (finding 6.2)

1. When a spare-parts (or similarly multi-table-capable) query doesn't name a specific equipment/component, render a short summary first (equipment/list name, pages, available-info columns) rather than dumping every matching table's full row content — matching the review's proposed two-step UX (summarize, then support a narrower follow-up).
2. This needs a genuinely general equipment/component-name matching heuristic (not hardcoded equipment names) — e.g. compare the question's noun phrases against each table's own section/heading text already captured at ingestion, falling back to "show everything" when no narrowing signal is found (preserving today's behavior as the safe default when the heuristic can't confidently narrow).
3. **Test** with synthetic multi-table fixtures under different equipment names, confirming narrowing works generically, not for one specific equipment name.

### Phase 6 — Strengthen reflection with deterministic, page-scope-aware checks (findings 5.1-5.3)

1. **Add the missing page-membership check**: extract cited pages from the final answer text/citations, compute `unexpected_pages = answer_pages - retrieved_pages` and `missing_pages = retrieved_pages - answer_pages`; a non-empty `unexpected_pages` should block ACCEPT outright (this is a correctness violation, not a quality nuance); a large `missing_pages` relative to retrieved evidence should at minimum lower the score materially, not just add a generic "incomplete" note.
2. **Add a duplicate-content check**: a simple near-duplicate-row detector (e.g. normalized-text similarity or exact-match-after-whitespace-normalization across rows in a rendered table) feeding into the score — this would have caught the maintenance table's near-verbatim duplicated rows from Section 3.1.
3. **Widen the scoring resolution**: replace the coarse boolean-average formulas with a finer-grained composite (e.g. real coverage ratios, not booleans) so genuinely different answers can't collapse onto the same score bucket — this is what would stop the "identical 0.8334 for two different bad answers" symptom from recurring even after 1-2 are fixed.
4. **Tests**: synthetic reflection inputs with known page mismatches and known duplicate rows, asserting the new checks fire and block/downgrade acceptance — independent of Phase 1's actual bug fix, so this becomes a permanent regression guard against a future evidence-scoping regression.

### Phase 7 — Fix or disable the strategy advisor (finding 5.4)

1. Preferred fix: change `_validate_concepts` from a literal substring-containment check to something that matches the advisor's own intended contract (short category/concept labels) — e.g. validate against a known vocabulary/enum of retrieval-strategy concepts (which the advisor's own prompt already uses) rather than requiring verbatim presence in the user's raw query text.
2. If a quick, confident fix isn't feasible this phase, disable the advisor behind its existing trigger conditions (feature-flag it off) rather than leaving it running and failing on nearly every real invocation — per the review's own suggestion, it's currently adding latency/trace noise with no observed benefit since deterministic routing already selects correctly on its own.
3. **Test**: extend the existing validator test with realistic paraphrased/category-label concepts (not just an exact-substring-friendly query) to catch this class of regression going forward — the existing test's blind spot (only testing the easy case) should itself be treated as a gap to close.
